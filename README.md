# Lena EOU

## Captura de regiones de ESI

El workflow **Capture ESI regions** consulta `GET /universe/regions/` cada 12 horas y también se puede lanzar manualmente. Respeta `Expires` y `Cache-Control`; cuando vence la caché, envía `If-None-Match` y aplica `Retry-After` y los límites de error de ESI.

La base `data/esi/uni/regions.db` contiene la tabla de datos `regions(region_id)`, sin nombres ni otros campos por región. Una tabla `metadata` conserva ETag y expiración para respetar la caché entre ejecuciones del workflow.

## Captura de órdenes de mercado por región

El workflow manual **Capture ESI market orders by region** usa `last_page` de `data/esi/mkt/headers.json` como estimación para planificar, sin hacer peticiones ESI previas solo para contar páginas. Si una región no tiene entrada en el JSON, se estima con una página. Asigna la región estimada con más páginas únicamente al worker 1 y reparte el resto por balanceo LPT entre los workers 2–4. Cada worker pide la página 1 al empezar la captura real y procesa las páginas secuencialmente; una región nunca se divide entre workers. El input booleano `force` de `workflow_dispatch` está desactivado por defecto. Sin `force`, si el `Last-Modified` de la página 1 coincide con el snapshot guardado, se vuelve a comprobar en los intentos 1–3, con 2,5 segundos entre los dos primeros, y se espera al `Expires` antes del cuarto y último intento; si sigue igual, conserva la DB existente. Con `force` activado, captura aunque coincida con el valor anterior, respetando primero cualquier `Expires` vigente de ESI. En ambos modos verifica que todas las páginas tengan el mismo `Last-Modified`; una inconsistencia usa los mismos reintentos y la espera hasta `Expires`. Para cabeceras ausentes o inválidas, registra el estado HTTP, los valores esperado y recibido (incluido `null`) y las cabeceras relevantes. Los errores y reintentos quedan visibles en los logs de Actions. Tras el último fallo, conserva la DB y la entrada de `headers.json` anteriores de esa región. Solo reemplaza su entrada de `headers.json` cuando publica la nueva DB de esa región con éxito.

Cada región se deduplica por `order_id` y se prepara como SQLite. Cuando terminan los workers se publican las bases completadas en `data/esi/mkt/[region_id].db.zst`, comprimidas con Zstandard nivel 22. Cada base contiene una sola fila en `capture(region_id, last_modified, order_count)` y todas las órdenes en `orders`, con los nombres de campo de ESI. `issued` y `range` se conservan como texto; `is_buy_order` se guarda como entero booleano `0/1`. Una tabla técnica `esi_cache` conserva `Expires` y `X-Pages` para respetar la caché entre ejecuciones.

`data/esi/mkt/headers.json` tiene una sola entrada por región: `last_modified` en ISO 8601 UTC, `last_modified_gmt` con la fecha HTTP original de la última página y `last_page` (el `X-Pages` final). `last_page` sirve como estimación para repartir regiones; la página 1 se solicita solo al empezar la captura real. Las peticiones incluyen `User-Agent`, respetan `Retry-After` y los límites de error de ESI; las regiones cuya caché siga vigente no se vuelven a solicitar.
